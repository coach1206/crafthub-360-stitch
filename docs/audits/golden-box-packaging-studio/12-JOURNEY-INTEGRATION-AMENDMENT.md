# Journey Integration Amendment

## Discovery audit

- **Golden Box route group** (`App.jsx`): `golden-box` index (rules/acknowledgement) → `competitions` (Hub) → `competitions/:competitionId` (Detail, eligibility/entry creation) → `entries/:entryId/blend` (`EntryWorkspace.jsx` — the real Build/Blend/Review/Presentation/Confirm flow) → `results/:competitionId` (Results) → `judge`/`judge/entries/:entryId` → `mentor/entries/:entryId`. Packaging Studio routes already sit in this same group (added in the prior pass).
- **`EntryWorkspace.jsx`** has 4 internal steps (`blend` → `review` → `presentation` → `confirm`), tracked as local component state, not separate routes. `review` is reached once all 4 required blend components (wrapper/binder/filler/vitola) are selected (`requiredMet`). This is the correct, real "Build Studio completion" signal — not a route change, a step-state condition.
- **Presentation readiness / submission readiness logic** lives in `entryService.validateSubmission()` (server-side) and the `confirm` step's UI (client-side pre-check mirroring the same required-components rule). Packaging is not currently part of either — this pass adds visibility into packaging status without altering `entryService.submitEntry`'s existing validation (a protected, already-proven system — see Scope Decision below).
- **Golden Box status cards**: `GoldenBoxHub.jsx`/`CompetitionDetail.jsx` read `entry.status` (draft/incomplete/eligible/submitted/etc. — an 13-state enum from migration 077). No packaging-derived status exists there; out of scope for this pass (competition-list cards, not the entry-workspace flow itself).
- **Journey/Golden Box resume mapping**: the 27-session spine's own resume logic (`session.js`) is untouched — Golden Box remains outside that spine, confirmed unchanged in Phase 9. Golden Box's own "resume" is simply reopening `/entries/:entryId/blend`, which now shows real packaging status in its `review` and `presentation` steps.
- **Back/next CTAs, deep-link handling**: `EntryWorkspace.jsx`'s step buttons are local `setStep()` calls, not route changes — "back" and "next" within the entry workflow were already safe (component state, not history). Packaging Studio's own routes (`/packaging-studio/:designId`) already enforce ownership server-side (Phase 8/Packaging-Studio-pass pattern) — a "direct deep link" to a design the caller doesn't own already returns an honest "not found or not accessible" state (built in the prior pass).
- **Existing Golden Box 7A / Phase 8 / Phase 9 / Packaging Studio tests**: read (not re-run yet) to confirm none of them assert on `EntryWorkspace.jsx`'s `review`/`presentation` step DOM in a way this addition would break (they assert on presence of specific fields/text already present — the new packaging block is additive, appended, not replacing any existing element).
- **Master checklist**: current state confirmed (`Golden Box Packaging Studio Production Completion` checked; `Phase 9 Journey Amendment — Packaging Studio Integration` present and unchecked — this pass's job).

## Before / after flow

**Before this pass:** `Build/Blend → Review → Presentation & Defense → Confirm/Submit` — Packaging Studio existed as a fully functional, independently-reachable module with no visible link from the entry workflow, and no way for a judge/mentor to see a submitted package without knowing its `entryId` by other means.

**After this pass:** `Build/Blend → Review (+ real Packaging Studio status card and CTA, shown once required components are selected) → Presentation & Defense (+ the immutable submitted packaging snapshot, when one exists) → Confirm/Submit → Results`. Judge review (`JudgeEntryReview.jsx`) now shows the submitted packaging snapshot as presentation evidence for assigned entries. Packaging Studio's own editor now shows real entry association, server-derived readiness, and a real "Submit Final Design" action gated on that readiness.

## Scope decision: packaging is not a hard gate on Golden Box entry submission

The mandate's "Journey Readiness Rules" section defines the minimum packaging requirements for progression but does not explicitly say Golden Box's own blend/entry submission (`entryService.submitEntry`, already gate-verified in Phase 8) must be blocked by incomplete packaging. Making packaging submission a hard prerequisite for entry submission would require changing `entryService.validateSubmission()` — a protected, already-proven system this pass's mandate explicitly instructs to preserve ("Preserve the completed Golden Box Packaging Studio backend... Do not add new Golden Box packaging features"). Blocking entry submission on packaging would also be a new, unapproved competition rule (learners who don't want to design packaging could no longer submit their blend at all).

This pass instead makes packaging **visibly required as a distinct step in the presented flow** (real status, real CTA, real submitted-snapshot display, real judge/mentor visibility) without changing the underlying blend-entry submission's own validation rules. This is disclosed here as a deliberate, safe scope choice — matching "use the smallest safe fix" — rather than silently narrowing the mandate's intent.

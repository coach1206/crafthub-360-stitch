# Incident Runbooks — Production Package 5

Each runbook: Detection → Confirmation → Containment → Recovery → Validation → Communication → Evidence preservation → Follow-up. All reuse this pass's real tooling (`server/lib/alertRules.mjs`, `/api/admin/ops-status`, `/api/health/*`, `scripts/backup-smokecraft-database.mjs`, `scripts/verify-smokecraft-backup-restore.mjs`, Package 2's payment reconciliation, `inventory_events` append-only ledger) rather than inventing new mechanisms.

## Application Down
Detection: `app_unavailable` alert fires (3 failed `/api/health/live` checks in 60s) or platform uptime monitor. Confirmation: `curl /api/health/live` from an independent network. Containment: none needed (read-only check). Recovery: check platform process logs, restart via platform dashboard/CLI, verify `DATABASE_URL`/secrets present (Package 4's `envValidator.js` fails fast if not). Validation: `/api/health/live` and `/api/health/ready` both 200 for 3 consecutive checks. Communication: status page (see `status-page.md`) if outage >15 min. Evidence: capture platform logs for the outage window before they roll off. Follow-up: post-incident review per `incident-severity.md`.

## Database Down
Detection: `db_unavailable` alert (2 failures in 30s) or `/api/health/ready` reporting DB failure. Confirmation: `pg_isready` / direct `psql` connection attempt. Containment: app should already be serving prototype-mode fallback for non-critical reads (existing `isDbAvailable()` behavior) — do not force writes during this window. Recovery: check managed-provider status page, restart local Postgres service if self-hosted, verify connection string unchanged. Validation: `/api/health/ready` 200, `SELECT 1` succeeds. Communication: SEV-1 — status page + internal page. Evidence: provider incident ID if applicable, timestamps of first/last failure. Follow-up: confirm no writes were lost (check `inventory_events`/`payment_audit_logs` for gaps around the outage window).

## Failed Deployment
Detection: GitHub Actions run fails, or `/api/version` doesn't update, or `/api/health/ready` fails post-deploy. Confirmation: compare `/api/version` commit to intended release commit. Containment: do not route traffic to the failed build (platform should already block promotion). Recovery: `scripts/rollback.sh` (Package 4) to the last known-good build. Validation: `/api/health/live`+`/ready`+`/migrations` all green on the rolled-back build. Communication: internal + release-owner. Evidence: CI logs, failing test/build output. Follow-up: fix forward, redeploy.

## Failed Migration
Detection: `migration_mismatch` alert (restored/running schema version doesn't match expected) or migration script exits non-zero. Confirmation: `SELECT filename FROM schema_migrations ORDER BY id DESC LIMIT 1` vs. expected latest file in `server/db/migrations/`. Containment: stop further deploys against this DB. Recovery: run the matching down-migration from `server/db/rollbacks/`, OR restore from the pre-migration backup (`--pre-migration` flag on `scripts/backup-smokecraft-database.mjs`) into an isolated DB first to confirm the rollback target, then apply to production. Validation: `scripts/verify-smokecraft-backup-restore.mjs`-style checks (migration version, critical tables, reconciliation) before declaring recovery complete. Communication: release-owner + on-call. Evidence: full migration output, `schema_migrations` row history. Follow-up: root-cause the migration defect before re-attempting.

## Payment Webhook Outage
Detection: `payment_webhook_failures` alert (3 failures in 600s) or Stripe dashboard delivery-failure notices (external, not exercised in sandbox — documented as a real production signal). Confirmation: check `payment_webhook_events`/`venue_cigar_payment_webhook_events` for a gap in expected event cadence. Containment: do not manually mark orders paid — wait for reconciliation. Recovery: Stripe automatically retries webhook delivery; once connectivity restored, replay via Stripe's dashboard (external) or Package 2's reconciliation job which polls Stripe's API as a backstop to webhook delivery. Validation: Package 2's reconciliation tooling reports zero paid-at-provider-but-unpaid-locally orders. Communication: payments-owner, SEV-1. Evidence: webhook event log gap window, Stripe dashboard event IDs (external). Follow-up: confirm no orders were fulfilled without payment confirmation during the gap.

## Duplicate-Payment Concern
Detection: `duplicate_payment_anomaly` alert (single-event, sev1). Confirmation: query `payment_intents_log`/`venue_cigar_payment_intents` for two successful charges against the same order/session. Containment: do not auto-refund — freeze the order for manual review. Recovery: use Package 2's canonical reconciliation tool to determine which charge is authoritative; issue refund for the duplicate via the same tool (never a manual, unaudited Stripe dashboard refund without a matching local record). Validation: reconciliation tool reports one active payment per order. Communication: customer notified per `payment-incidents.md` template. Evidence: both payment intent IDs, timestamps. Follow-up: identify the client/retry bug that caused the duplicate submission.

## Object-Storage Outage
Detection: `object_storage_unavailable` alert (3 failures in 60s) from the storage adapter's error rate. Confirmation: direct adapter health check / provider status page (external). Containment: media uploads queue/fail gracefully (Package 4's adapter should not crash the app on storage failure — verify this holds). Recovery: wait for provider recovery or fail over to replication target if configured. Validation: successful test upload + fetch. Communication: media-owner, SEV-1/2 depending on duration. Evidence: adapter error logs. Follow-up: confirm no orphaned DB rows point to un-uploaded media.

## Broken Images / Media-Processing Backlog
Detection: `image_processing_backlog` alert (queue depth ≥50 for 900s) or user reports. Confirmation: check Sharp pipeline job queue depth, spot-check reported broken image URLs. Containment: none needed (read path). Recovery: restart the background-job worker, re-run failed jobs. Validation: queue depth returns to baseline, spot-checked images load. Communication: media-owner, SEV-3 typically. Evidence: failed-job list with error messages. Follow-up: identify root cause (bad source file vs. pipeline bug).

## Passport Claim Failure
Detection: `passport_claim_failure_spike` alert (≥10% failure rate over 10 samples in 600s). Confirmation: check `passport_360_sync_audit_log` for the failure pattern; distinguish real defects from the known pre-existing legacy-script issue (see `passport-known-issue.md` — NOT the same thing as a live customer-facing spike). Containment: none needed (claims are idempotent server-side eligibility checks). Recovery: identify and fix the root cause; if it's session-completion-ledger related, cross-check with the fresh-player closure suite. Validation: failure rate returns below threshold. Communication: gameplay-owner. Evidence: failed claim attempts with correlation IDs. Follow-up: post-incident review if SEV-2.

## Golden Box Failure
Detection: `golden_box_lifecycle_failure` alert (3 failures in 600s). Confirmation: check `golden_box_activity_log`/`golden_box_entries` for stuck submissions. Containment: none needed. Recovery: identify stuck-state entries, use support admin tools (`support-admin-tools.md`) to inspect (read-only) and, if a genuine corrective action is needed, apply it through the audited corrective-action flow tied to a support case. Validation: entry lifecycle resumes normally. Communication: gameplay-owner. Evidence: entry ID + activity log. Follow-up: root-cause.

## High Error Rate
Detection: `elevated_5xx_rate` alert (≥5% over 20+ samples in 300s). Confirmation: check recent deploy correlation (did this start right after a release?). Containment: consider rollback if deploy-correlated. Recovery: rollback or hotfix. Validation: error rate returns below threshold. Communication: on-call, SEV-2. Evidence: sample of failing request logs (correlation IDs). Follow-up: root-cause.

## Rate-Limit Lockout
Detection: `abnormal_rate_limit_activity` alert (25+ events in 300s) or a legitimate user reports being locked out. Confirmation: check `securityEventService` logs for the IP/account pattern — distinguish attack from a legitimate burst (e.g. shared venue IP). Containment: none needed (rate limiter already protecting). Recovery: adjust limiter config or allowlist a legitimate IP if confirmed safe. Validation: legitimate traffic resumes. Communication: security-owner. Evidence: request pattern, IPs, timestamps. Follow-up: tune thresholds if false-positive rate is high.

## Compromised Secret
Detection: secret found in a log, a leaked commit, or suspicious activity tied to a known key. Confirmation: identify which secret and how exposed. Containment: rotate immediately (see `secret-rotation.md`) — do not wait for a scheduled window. Recovery: rotate, invalidate old sessions/tokens tied to the compromised secret. Validation: old secret no longer accepted, new secret working. Communication: SEV-1, founder + security-owner immediately. Evidence: preserve the exposure evidence (log line, commit SHA) before scrubbing it from active systems. Follow-up: REQUIRED post-incident review, audit for any misuse during the exposure window.

## Suspected Unauthorized Access
Detection: `securityEventService` anomaly, unexpected admin/founder action, RBAC bypass attempt. Confirmation: review `support_case_actions`/security-event audit trail for the actor. Containment: revoke session/JWT for the suspect actor, force password/PIN reset. Recovery: audit all actions taken by that actor during the suspected window. Validation: no unauthorized state changes found, or all found are reversed. Communication: SEV-1, founder immediately. Evidence: full audit trail export. Follow-up: REQUIRED post-incident review.

## Backup Failure
Detection: `backup_failure` alert (single failed run, sev1). Confirmation: `backup_run_log` shows `status='failure'` with error detail. Containment: none needed (doesn't affect live app). Recovery: fix the underlying cause (disk space, DB connectivity, `pg_dump` version mismatch) and re-run `scripts/backup-smokecraft-database.mjs` immediately — do not wait for the next scheduled run. Validation: next run succeeds, `backup_run_log` shows `status='success'`. Communication: db-owner. Evidence: full error output. Follow-up: confirm no backup gap exceeds the RPO target (`rpo-rto.md`).

## Restore Failure
Detection: `restore_verification_failure` alert (any check in `verify-smokecraft-backup-restore.mjs` fails). Confirmation: review the specific failed check(s) in the script's output/JSON. Containment: the restore only ever targets an isolated test DB, so a failed restore never touches production — no containment action needed on the live system. Recovery: identify why (corrupt artifact? schema drift? reconciliation mismatch?), take a fresh backup, re-run the validator. Validation: `verify-smokecraft-backup-restore.mjs` exits 0. Communication: db-owner, sev1 (backups whose restorability hasn't been proven are not real backups). Evidence: full validator output/JSON. Follow-up: REQUIRED review of backup process if this is not a one-off.

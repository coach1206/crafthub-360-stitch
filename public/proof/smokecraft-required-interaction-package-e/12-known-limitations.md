# 12 — Known Limitations

- **Client-side eligibility hint is not the security boundary.** `PassportStamp.jsx`'s local `isEligible` (used only to enable/disable the "Claim Your Stamp" button and to decide whether to preemptively surface an eligible/ineligible UI state) is still computed from the local `GuestSessionContext` completedSteps journal, not a live server call. This is a UI convenience only — the REAL gate is the server's `checkEligibility(req)` inside `/claim` and `/eligibility`, verified independently in this pass (see doc 03). A stale or manipulated local journal can at most make the button visually enabled or disabled incorrectly; it can never cause a real claim to succeed without real server-side evidence.
- **No separate Passport-claim-specific audit log exists.** `passport_360_sync_audit_log` covers sync/link events, not individual per-stamp claims. The real, existing ledger for a claim is the `passport_360_earned_stamps` row itself (one real, `dedupe_key`-enforced row per real claim) plus `smokecraft_award_audit` for the tied Session 23 completion — this pass did not invent a new audit mechanism, consistent with "reuse the canonical Passport/reward services, don't build a second system."
- **`awardSessionRewards()`'s fire-and-forget server sync remains an established, pre-existing pattern**, not something Package E changes: the local optimistic completedSteps update happens regardless of whether the server call ultimately succeeds. A network failure at that exact moment could leave the local journal ahead of the server truth until the next successful sync. This has been an accepted, disclosed pattern since Holistic Fix 4 and applies identically to every other required-interaction package (A-D); Package E does not introduce or worsen it.
